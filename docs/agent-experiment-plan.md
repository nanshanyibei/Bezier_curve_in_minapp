# Agent 实验版方案（小程序 + 微信云开发）

> 结论：**可行，且微信云开发是当前最合适的载体**。但有一条硬红线必须先认清（见第一节），
> 以及 Agent ≠ 一次 `chat/completions`，需要 6 个部件（见第三节）。
> 日期：2026-11-16

## 一、先认红线：个人主体不能上线 AI 问答

| 事实 | 影响 |
|---|---|
| 「深度合成 - AI 问答」类目 **只向企业/非个人主体开放** | 个人主体小程序提审 AI 对话功能必被驳回 |
| 申请该类目需提供《互联网信息服务算法备案》 | 自主备案 3~13 万元，个人走不通 |
| 只有**提审/发布**才校验类目 | **开发版、体验版不校验** |

**所以「实验版」的正确定义 = 跑在开发版/体验版，自用 + 朋友圈内测，永不提审。**
这条路零资质、零成本、完全合法。真要做成产品再注册个体工商户（¥300~800/年）换主体。

> 另外：即使换成企业主体，云开发控制台的 AI 板块能直接生成算法备案材料，不用自己跑备案流程。

## 二、为什么微信云开发适合做 Agent 载体

| 能力 | 微信云开发 | 说明 |
|---|---|---|
| 模型调用 | `wx.cloud.extend.AI`（内置混元，套餐含 10 万 token/月）或云函数出网直连 DeepSeek/硅基流动 | 云函数出网**不受 request 白名单限制**，这是相对现在最大的解放 |
| 免域名 | ✅ | Agent 必须频繁调接口，域名备案这条路直接绕开 |
| 会话存储 | 文档型数据库 | 按读写次数计费，不按核时 |
| 流式输出 | 基础库 2.20.2+ `enableChunked` + `onChunkReceived` | 注意：真机与开发者工具表现不一致，真机常是整段返回 |
| 内容安全 | `security.msgSecCheck` | 审核/合规必备，实验版也建议接 |
| 语音/图片 | 云存储 + AI 能力 | 可选 |

## 三、Agent 到底要做哪些工作

一个能跑的最小 Agent（不是聊天机器人）需要 6 件东西：

| # | 部件 | 在本项目里的具体做法 | 工期 |
|---|---|---|---|
| 1 | **模型接入** | 云函数 `agent`，出网调 OpenAI 兼容接口；key 存环境变量 | 0.5 天 |
| 2 | **工具集（function calling）** | 4 个工具，直接复用现有数据层（见第四节） | 1 天 |
| 3 | **循环调度** | 云函数内 while 循环：模型要工具 → 调工具 → 结果回灌 → 继续，最多 3 轮，防云函数 60s 超时 | 0.5 天 |
| 4 | **会话存储** | `chats` 集合：`{ _openid, sessionId, messages[], updatedAt }` | 0.5 天 |
| 5 | **长期记忆** | 把日记/足迹统计做进 system prompt（不是向量检索，20MB 数据直接摘要够用） | 0.5 天 |
| 6 | **对话 UI** | 新页面：消息气泡 + 打字机 + 工具调用状态提示（"正在查景点…"） | 1 天 |

合计 **约 4 天**，其中 3、4、6 可以在 P0 之后并行。

## 四、工具设计（这是本项目最值钱的部分）

你已有的数据结构天然就是 Agent 的工具箱：

```js
// 1. 查景点（复用 attractions 集合 + 5A 本地数据）
searchAttractions({ province, city, keyword, tags, limit })

// 2. 查/算路线（复用 routeStore + haversine）
planRoute({ from, to, stops[], mode: 'drive' })
  → { km, days, suggestedStops[] }

// 3. 查足迹（复用 marks）
getFootprint({ province, status: 'been'|'want', year })
  → { visited: [], want: [], count }

// 4. 写日记/回忆（复用 diaries，需用户确认后写入）
saveMemory({ adcode, title, content, date })
```

对应可实现的用户意图：
- 「我 3 月想去成都，帮我排个 3 天路线」→ searchAttractions + planRoute + getFootprint（避开去过的）
- 「我今年去过哪些省？」→ getFootprint
- 「把这次旅行写篇日记」→ saveMemory（先出草稿给用户确认，不要直接写库）

## 五、技术坑位（提前避开）

1. **云函数 60s 超时**：Agent 多轮工具调用容易超。限制 `maxToolRounds = 3`，每次工具调用设 8s 超时；复杂任务拆成两段提交。
2. **流式在真机不可靠**：`onChunkReceived` 在开发者工具分块、真机常整段。P0 先用「整段返回 + 前端打字机动画」假装流式，体验足够，代码量少一半。
3. **工具调用的稳定性**：DeepSeek 等模型的 JSON 参数偶尔不合规，工具层必须做入参容错（缺字段给默认值，不抛错给模型）。
4. **不要自动写库**：任何 `saveMemory` 这类写操作都先返回草稿让用户点确认，避免污染真实数据。
5. **内容安全**：回复落库前过 `msgSecCheck`；实验版也接，避免以后迁移返工。
6. **成本**：云函数出网流量 800 点/GB，但 LLM 响应只有几 KB，可忽略；真正花的是模型 token（走自己 key 就按 DeepSeek 价，一次对话约 ¥0.001~0.01）。

## 六、路线图

**P0（1 天）跑通单轮工具调用**
- 云开发环境开通 → 云函数 `agent` → 1 个工具 `searchAttractions` → 对话页最小版
- 验收：输入「成都必去哪些地方」，能返回真实景点数据

**P1（2 天）多轮 + 4 个工具 + 会话**
- 加 `planRoute` / `getFootprint` / `saveMemory`（草稿确认）
- `chats` 集合存会话，支持历史会话列表

**P2（1 天）体验打磨**
- 打字机效果、工具调用状态提示、`msgSecCheck`、错误兜底
- 生产构建继续剥离（`@dev` 块），不污染正式包

## 七、与「迁微信云开发」的关系

**同一次迁移，顺手把地基打好。** Agent 依赖的东西（`wx.cloud` 调用、`_openid` 归属、文档型库、云函数出网免白名单）正是迁移后才有。所以顺序应该是：

1. 迁数据层（1~1.5 天，见 `docs/migrate-to-wxcloud.md`）
2. P0 Agent（1 天）
3. P1 / P2 迭代

反过来，留在现在的腾讯云 CloudBase 上做 Agent：每加一个接口都要过域名白名单，且 PG 核时按实例计费——做实验会很快烧光额度。**先迁，再建 Agent。**
