# Agent 实验版：载体方案全对比（含返工风险）

> 上一版只给了「迁微信云开发」一条路，这版把可选空间铺开，并给出「换载体不用重写」的架构切法。
> 日期：2026-11-16

## 一、先说结论

| 阶段 | 选什么 | 理由 |
|---|---|---|
| **实验期（本周验证 Agent 值不值）** | **方案 E：本地 dev server**（手机走调试模式连本机） | 0 成本、0 迁移、当天出结果。Agent 的成败在 prompt/工具设计，不在基础设施，别先花 1.5 天搬数据 |
| **定型期（确定要继续做）** | **方案 B：微信云开发云托管（容器）** | 真流式、无 60s 限制、Docker 可直接搬走，返工风险最低 |
| 定型期备选（最省事） | 方案 A：wx.cloud 云函数 | 免费额度大、免备案，但锁微信生态、受 60s 限制 |
| 不推荐 | 方案 C / H | 已经踩过的坑，或绕不过审核 |

关键：**先把 Agent 逻辑写成「与载体无关的一层」**（见第五节），这样无论最后落 A、B 还是 F，UI 和工具代码一行不改。

## 二、六个载体方案

### A. 微信云开发 · 云函数（wx.cloud.callFunction）

| 项 | 内容 |
|---|---|
| 架构 | 小程序 → `wx.cloud.callFunction('agent')` → 云函数里跑工具循环 → 文档型数据库 |
| 优点 | 免域名免备案；openid 自动；免费环境 40,000 点/月；部署最简单（右键上传） |
| 缺点 | **云函数 60s 上限**（Agent 多轮易撞）；无原生 SSE，只能靠 `enableChunked` 且真机不稳；绑定 wx.cloud SDK |
| 长期成本 | 6 个月后 ¥19.9/月 |
| 上手 | 1 天（含环境开通） |
| **返工风险** | **中**：锁微信生态。将来想搬去 Web/H5/其他平台，transport 层要重写（业务逻辑可留） |

### B. 微信云开发 · 云托管（容器）

| 项 | 内容 |
|---|---|
| 架构 | 小程序 → 云托管服务（Node/Java 容器）→ 标准 HTTP/SSE → 自带数据库或外接 |
| 优点 | **真 SSE 流式**；无 60s 限制（可跑几分钟的 Agent）；任意语言；Docker 化，可原样搬去任何服务器/K8s；有固定出口 IP |
| 缺点 | 按 CPU/内存/时长计费，比云函数贵；有冷启动（可配最小实例）；要写 Dockerfile |
| 长期成本 | 低配约 ¥30~80/月（看常驻实例） |
| 上手 | 2 天 |
| **返工风险** | **低**：容器是行业通用形态，换平台只改部署，不改代码 |

### C. 腾讯云 CloudBase 通用版（现状）+ 备案域名

| 项 | 内容 |
|---|---|
| 架构 | 现在的 wxauth 网关 + PG/pgdoc + genAttraction |
| 优点 | 代码已写好，不用动 |
| 缺点 | 必须买域名 + ICP 备案（1~20 工作日）；PG 按核时计费，额度必爆；pgdoc 双查浪费；请求要过 request 白名单 |
| **返工风险** | **高**：已经踩过两轮坑（域名、资源点），继续投入等于继续填坑 |

### D. 纯前端直连 LLM（开发版/体验版 + 调试模式）

| 项 | 内容 |
|---|---|
| 架构 | 小程序页面直接 `wx.request` 到 DeepSeek/硅基流动，key 存在 storage |
| 优点 | **0 后端、0 迁移**，半小时能跑通；适合验证「模型能不能理解你的数据」 |
| 缺点 | key 暴露在客户端（只能自用）；工具循环要在前端跑（页面逻辑变重）；模型多轮 + 工具调用受 60s 影响；关掉调试模式就废 |
| 长期成本 | ¥0（只花 token） |
| 上手 | 0.5 天 |
| **返工风险** | **极低**：prompt、工具定义、JSON schema 全部可复制到正式后端，只废掉 transport 那 30 行 |

### E. 本地 dev server（Node 起在本机，手机连同一 WiFi）

| 项 | 内容 |
|---|---|
| 架构 | 本机 `node server.js`（Express/Fastify）→ 跑完整 Agent 循环 → 手机 `wx.request('http://192.168.x.x:3000/agent')`（开发版开调试模式即可） |
| 优点 | **完整 Node 环境**：真 SSE、任意 npm 包、断点调试、日志随便打；改代码秒生效不用部署；0 成本 |
| 缺点 | 手机必须同网段或内网穿透；只能自己/身边人用；不能给外部用户 |
| 长期成本 | ¥0 |
| 上手 | 0.5 天（含一个最小 HTTP server） |
| **返工风险** | **低**：这套 server 代码就是将来云托管（方案 B）的容器入口，能整体搬走 |

### F. 自购轻量服务器 + 备案域名 + Node

| 项 | 内容 |
|---|---|
| 架构 | 腾讯云轻量（¥50~100/年新客）→ Node 服务 → HTTPS + 备案域名 → 小程序 request 白名单 |
| 优点 | 完全可控、便宜、真 SSE、可给别人用、不锁任何平台 |
| 缺点 | **仍要 ICP 备案**（1~20 工作日）；自己维护 HTTPS 证书续期、进程守护；出故障自己扛 |
| 长期成本 | ¥100~300/年 |
| 上手 | 1 天（备案时间另算） |
| **返工风险** | **低**：标准 Linux + Node，随时迁 |

### G. 云开发 AI+（`wx.cloud.extend.AI` 内置模型）

| 项 | 内容 |
|---|---|
| 架构 | 前端直接调云开发内置模型能力，不碰第三方 key |
| 优点 | 免 key、内网直连、套餐内含 10 万 token/月、控制台能直接生成算法备案材料 |
| 缺点 | 模型选择少（混元为主）；function calling 支持不如 DeepSeek 灵活；仍锁微信；Agent 复杂编排能力弱 |
| **返工风险** | 中：适合做「问答型」不适合做「多工具编排型」Agent |

### H. H5 + web-view / 公众号内嵌

| 项 | 内容 |
|---|---|
| 结论 | **不可行**。web-view 需业务域名（照样备案 + 校验文件），且 AI 生成内容审核口径不变；个人主体仍申请不了类目 |

## 四、各方案的「返工触发条件」（重点看这列）

| 方案 | 什么情况下必须返工 |
|---|---|
| A 云函数 | ① Agent 单轮耗时 > 55s ② 需要真流式 ③ 想上 Web/H5/其他平台 |
| B 云托管 | ① 用量涨到嫌贵 ② 想换云厂商（改部署，不改代码） |
| C 现状 | ① 域名备案等不起 ② 额度再爆 ③ 想换后端 —— 大概率 3 个月内全中 |
| D 前端直连 | ① 想给别人用（key 暴露）② 工具超过 2 个（前端逻辑爆炸） |
| E 本地 server | ① 想让朋友直接用（手机不同网段）② 需要 7×24 在线 |
| F 轻量 | ① 备案被拒（个人主体做 AI 服务可能被问用途）② 运维出事故 |

**规律：越靠「平台内」越省事但越锁；越靠「容器/标准 HTTP」越自由但要多配一点。**
防返工的解法不是选对方案，而是把逻辑放在两者之间（下一节）。

## 五、防返工架构：三层解耦

```
pages/agent/            UI 层：只认 send()，不关心后端是谁
   ↓
agent/core/             AgentCore：prompt + 工具定义 + 循环 + JSON 容错
   ↓                    （纯 ESM，只依赖 fetch，无框架、无 SDK）
agent/transport/        适配器：direct | local | wxcloud | https
```

`AgentCore` 只是一个函数：

```js
// agent/core/index.js —— 三种宿主都能直接跑
export async function runAgent({ messages, tools, callModel, maxRounds = 3 }) {
  for (let i = 0; i < maxRounds; i++) {
    const res = await callModel({ messages, tools });
    if (!res.toolCalls?.length) return res.content;
    for (const call of res.toolCalls) {
      const out = await tools[call.name](safeParse(call.args));
      messages.push({ role: 'tool', name: call.name, content: JSON.stringify(out) });
    }
  }
  return '这个任务有点复杂，我先给出部分结果…';
}
```

`callModel` 由适配器注入：

```js
// transport/direct.js   开发版前端直连
// transport/local.js    http://192.168.x.x:3000/agent
// transport/wxcloud.js  wx.cloud.callFunction({ name: 'agent' })
// transport/https.js    云托管 / 轻量服务器
```

这样一来：

- 换载体 = 换 30 行适配器，`core` 和 `pages` 不动
- 方案 D（0.5 天）→ 方案 E（0.5 天）→ 方案 B（2 天）是**渐进升级**，不是推倒重来
- 工具定义（4 个 schema）全程复用，那才是最花时间的部分

## 六、推荐落地顺序

| 步 | 做什么 | 产出 | 耗时 |
|---|---|---|---|
| 1 | 写 `agent/core`（prompt + 4 个工具 schema + 循环） | 与载体无关的纯逻辑 | 1 天 |
| 2 | 接 `transport/direct`（前端直连 DeepSeek），开发版跑通 | 能对话、能调工具 | 0.5 天 |
| 3 | 接 `transport/local`（本机 Node server），拿到真 SSE + 好调试 | 打字机效果 + 工具日志 | 0.5 天 |
| 4 | 判断值不值：好用 → 继续；不好用 → 只废了 2 天，没迁任何数据 | 决策点 | — |
| 5 | 值 → 落 `transport/wxcloud`（云函数）或 `https`（云托管容器） | 可对外用 | 2 天 |
| 6 | 数据层迁移（`docs/migrate-to-wxcloud.md`） | 与 Agent 解耦，可并行/可延后 | 1.5 天 |

**关键变化：数据层迁移从「前置条件」降级为「可延后项」。** Agent 实验阶段完全不需要碰数据库——工具先读包内静态数据（5A 景点、路线）就能验证核心价值。
